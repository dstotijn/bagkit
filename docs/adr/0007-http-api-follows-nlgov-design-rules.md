# Design the HTTP API to the NLGov API Design Rules, described with OpenAPI

The first HTTP API was carried over from the tool bagkit started from: unversioned paths such as `/9902HA/1` and `/52.21/5.96`, a bare JSON array, snake_case fields and `{"error": ...}` bodies, with no machine-readable description. BAG data mostly serves Dutch public-sector users, whose APIs are expected to follow the NLGov REST API Design Rules (ADR 2.2) and their Geospatial module. We rebuilt the API to those rules instead of patching the old paths. The result is a `/v1` base path, resources named with nouns (`/adressen`, `/adressen/{nummeraanduidingIdentificatie}`, and `/adressen/_dichtstbij` as an operation), camelCase query keys and fields, problem details (RFC 9457) that list every invalid parameter, an `API-Version` header and security headers on every response, GeoJSON points with CRS negotiation (`crs`, `puntCrs`, `Content-Crs`), and an OpenAPI 3.0 description served at `/v1/openapi.json`.

Resources, fields, parameters, messages and the OpenAPI description are in Dutch, with the BAG's terms (ADR-0008). We deviate in three places. The documentation site stays in English, which the rules allow for existing documentation. `bagkit serve` speaks plain HTTP and relies on a reverse proxy for TLS. The description names bagkit's maintainer and issue tracker as its contact, not the organisation that runs a server.

## Consequences

- The old paths are gone. Clients and `bagkit query` use the `/v1` requests, and `bagkit query` routes them through the same code as the server.
- `src/openapi.json` is written by hand and is the contract. Tests check every response the live server returns against its schemas, rejecting fields and patterns it does not document; `tests/openapi.rs` checks that its paths and query parameters are exactly those in `api::RESOURCES`, that each operation routes with its example values, and that its example response has a real response's shape; and a unit test checks that its version matches `api::VERSION`. `mise run api:check` runs the DON Checker from developer.overheid.nl on it.
- The API has its own semantic version, `api::VERSION`, which sets `info.version`, the `API-Version` header and the `/v1` path; a test keeps them in step. It is independent of the crate version, so a CLI or library release does not move the API's path. An incompatible API change needs `/v2`. Compatible changes raise the minor or patch version, and the HTTP API reference page keeps the changelog.
- OpenAPI 3.1 would let the schemas be plain JSON Schema, but 3.0 is the version on the Dutch comply-or-explain list, and the DON Checker warns about 3.1.
- An adreslijst answers the same address resources with fewer fields, and answers nearest lookups with 501.
